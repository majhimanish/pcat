# v5.1 — the linter on real codebases

Spec: `docs/specs/v5.1-linter-real-code.md`. No new agent runs: everything below re-scores
data that already existed (v5's 144 in-repo runs, the v4 / v4.1 feedback runs, the v3
samples) or lints code humans already wrote (CTFd, healthchecks, LNbits at their pinned
commits). Canonicalization, fingerprints, every `impl.py`, the search threshold and all
earlier experiment files are unchanged. Data: `experiments/v5.1/` (`rescore/`, `survey/`,
each with a README). Decisions: `DECISIONS.md` 203–225.

## Summary

- **The v5 false CI failures are gone.** With the v5.1 linter, 0 of 72 pcat runs would
  fail CI (v5: 5). The 3 LNbits runs that reproduced the original function exactly now
  pass; so do the 2 CTFd reset-token runs, whose code was as safe as the pattern.
- **On marked code the linter is now trustworthy for these 144 runs**: no run fails CI,
  and every high deviation left (16 across both conditions) is on inferred, advisory
  findings.
- **Inferred findings on real code are mostly noise.** In a random sample of 90
  medium/high findings on untouched app code, 0 were true deviations, 15 debatable,
  75 false positives, nearly all from inference attaching a function that does not
  derive from any pattern. Inferred findings never fail CI, but they should not be shown
  in a PR by default.
- **Lab results do not move**: v3 samples, v4 and v4.1 feedback runs score identically
  under v5.1 and v4.1, so every v4.1 / v5 Part A headline stands.

## What was fixed

| Part | Problem seen in v5 | Fix |
|---|---|---|
| A | A class defined in the linted module (`KeyChecker` in `lnbits/decorators.py`) resolved to a bare name; the pattern's import of it resolved to `lnbits.decorators.KeyChecker`: guard violated, false CI failure | One symbol table per code unit: imports (any alias, incl. `if TYPE_CHECKING:` / `try:` imports), same-file classes, functions and constants, attribute chains. Same-file names resolve to `<module>.<name>` from the file's path, so pattern side and code side agree. Loose names are bound across the two sides; a helper one side defines and the other imports is compared as the import. Unqualified guard targets match a same-file definition |
| B | `check_code` on a single function (no imports) reported a library swap | Unknown names are assumed only where the pattern binds the same name; rules depending on the rest are skipped and listed (`skipped_rules`); `resolution: full / partial`; `context` (imports or the whole file) and `file_path` (inside the served repo, `pcat serve --repo`) restore full resolution; server instructions say to pass imports as `context` |
| C | Patterns listing a framework they never import made PC103 fire on every derived function (fixed by hand in v5) | Validation check 12 (`requires` covers every third-party import and every entry is imported; stdlib exempt); `import_names` mapping with a built-in table (pyjwt → jwt, …); catalog-level `first_party` in `catalog/catalog.yaml`; PC103 counts a swap only when code drops a required library the pattern itself uses at run time |
| D | Guard too narrow for a legitimate sibling (CTFd reset token) | Guard review of every guard that fired (below); `match: any` for guards; PC102 reports "same check, different exception" as medium instead of "check removed" (high) |
| E | Found by the survey: methods compared with `self` as a parameter; nested wrappers reported twice; `(conn or db).execute` vs `db.execute` seen as a removed and an added call | All three fixed, each with a regression test that fails on the previous commit |

Check 12 found 22 v5-catalog patterns that import the app's own package (`CTFd`, `hc`,
`lnbits`); fixed by declaring it first-party (metadata only). The main catalog passed.

## Is the linter now trustworthy enough to be a required CI check?

**For marked code, yes, with a narrow scope**: `pcat lint --changed-since <base>
--fail-on high` without `--include-inferred`. On the 144 v5 runs it fails no correct code,
all 5 earlier false failures are explained and fixed, and the failures it still produces
on lab data (dropping 429, swapping libraries) are real decisions a human should make.
Caveats: 144 runs on three apps and self-reviewed catalogs; one model; guards are only as
good as their review (one of the five that fired in v5 was too narrow).

**Inferred findings should stay advisory and off by default in PRs.** On untouched code
they were 75 of 90 false positives in the sample (83%) and 0 true deviations. A team shown 300
"no longer calls `.first`" comments on code nobody changed would switch the check off.

What would still make teams switch it off:
- Inference noise if `--include-inferred` is turned on in CI (the threshold 0.56 was
  calibrated on lab code; app code is full of short functions in the house style).
- Guards written too narrowly for sibling uses, until someone reviews them.
- Low-severity churn (PC108/PC110) on functions that changed for unrelated reasons.
- A marker placed between decorators and `def` is not recognized, so the function is
  only inferred (seen once in v5; KNOWN_GAPS).
