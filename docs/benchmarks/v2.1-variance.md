# v2.1 — LLM output variance experiment: results

Spec: `docs/specs/v2.1-variance-experiment.md`. Data: `experiments/variance/`
(prompts in `tasks.yaml`, samples in `runs/main/`, analysis in
`runs/main/analysis.json` and `table.md`, browsable `pcat mine` reports in
`runs/main/mine-{A,B,C}/report.html`, references in `references/`).

## Setup

| | |
|---|---|
| Backend | headless Claude Code CLI, `claude -p` (v2.1.316); no `ANTHROPIC_API_KEY` was available, so the API backend was not used |
| Model | `claude-sonnet-5-5` (requested and reported for all 480 samples) |
| Temperature | CLI default; the CLI does not expose it, so it is recorded as `null` |
| Samples | 8 tasks × 3 conditions × 20 = **480**; all generated, 0 failures, 0 retries |
| Date | 2026-11-02, generated between 06:55 and 07:10 UTC (smoke run first) |
| Isolation | one process per sample, each in a new empty directory; no session persistence, no MCP servers, all tools disallowed, extra CLAUDE.md directories removed from the environment |
| Prompts | `tasks.yaml`, committed (`80ee26e`, 06:51 UTC) before the first sample (06:55 UTC) |
| Cost | $19.58 as reported by the CLI |

Conditions: **A** the same prompt 20×; **B** 5 paraphrases × 4; **C** the B
paraphrases plus a reference implementation and the instruction "Follow this
reference implementation; adapt names and details only where the request
requires it".

How code is compared: each sample's extracted code is canonicalized by the
existing rules (names, comments, docstrings and formatting removed) and its
**shape** fingerprint blanks literal values. Module-level statements such as
`app = FastAPI()` are moved aside and their names normalized (DECISIONS #94), so
two samples have the same shape only if their code has the same structure.

### Limitations of this setup

- **One model, one backend.** Every sample is Claude Sonnet 5.5 through Claude
  Code. Other models, or the same model with a different system prompt, may vary
  more or less.
- **Not a bare model call.** Each sample sees Claude Code's own system prompt
  and a small context injected by the hosting environment (user e-mail,
  commit-attribution guidance). No project files or CLAUDE.md were visible (a
  probe confirmed this). The temperature is unknown.
- **The CLI layer leaked into 2 samples.** Two `jwt_create` C samples are not
  code: the CLI answered as its `/security-review` skill ("needs to run inside
  a git repository"). They are kept and counted invalid. 31 samples took 2–3
  turns despite all tools being disallowed (most likely denied tool attempts);
  their responses are ordinary code answers.
- **The "no classes" instruction conflicts with idiomatic FastAPI.** 19/20 (A)
  and 18/20 (B) `fastapi_create_user` samples define Pydantic models, and
  10/20 (A) and 5/20 (B) `env_config` samples define an exception class. By
  the spec's rule those are invalid, so the headline numbers for those two
  tasks rest on 1–15 samples. A supplementary metric fingerprints them with
  classes removed (below).
- **20 samples per cell** is small. With 20 samples, "20 distinct shapes" is the
  maximum, so A and B often hit the ceiling and cannot show *how much* more
  diverse one is than the other.
- **Shape equality is strict.** A one-token change counts as a new shape (the
  two most similar distinct `jwt_create` A samples differ only in `exp + ttl`
  vs `exp + int(ttl)`). Supplementary similarity metrics (below) show how far
  apart the shapes really are.
- **References were picked mechanically from B.** Every B shape was unique for
  seven tasks, so the spec's rule ("most common shape, …, lowest sample
  number") fell back to B sample 01 there. The references are arbitrary,
  unreviewed model outputs, not curated patterns.
- **The reference sits in the prompt.** Condition C simulates a perfect lookup:
  the right reference is always provided. A real MCP flow also has to find it.

### How the variants differ (conditions A and B)

Library choice is mostly stable; structure and details are not. Counts below
are samples out of 20.

- **`jwt_create`** — Always PyJWT. In A, all 20 add `iat`, `nbf`, `jti`
  (`uuid4`), issuer and audience, and validate inputs. They differ in time
  handling and small details: `now = datetime.now(timezone.utc)` vs
  `now = int(time.time())`, secret from the environment (17) or a parameter.
  Paraphrasing changes the design more: `jti` drops to 11, and 8 of 20 B
  samples split the work into 2–3 functions.
- **`password_hash`** — Never a third-party library (no bcrypt/argon2/passlib):
  always `hashlib`, `os.urandom` salts, `base64`, a `$`-joined format and
  `hmac.compare_digest`. The real split is the algorithm:
  `hashlib.scrypt(...)` in 11 A samples vs `hashlib.pbkdf2_hmac(...)` in 9 (B:
  18 vs 2). That's why A's 17 shapes collapse into 2 near-shape groups.
- **`paginate_query`** — Always SQLAlchemy, `func.count()` over a subquery,
  `offset`/`limit`, `ValueError` on bad input. Variants differ in return type
  (`return items, total` vs a dict with page metadata), whether
  `order_by` is enforced, and whether a helper inspects the query's entities
  (7 of 20 in A). 20 shapes and 14 near-shape groups in A: genuinely different
  implementations.
- **`http_retry`** — The same prompt always picks `requests`, jitter
  (`random.uniform`), 429 handling and `raise_for_status`; 16 of 20 honour
  `Retry-After`. Paraphrases change the library: 8 of 20 B samples use
  `urllib.request.Request(...)` from the standard library instead of
  `requests.get(...)`, and `Retry-After` drops to 7.
- **`env_config`** — Always `os.environ`, but the error convention differs:
  `raise ValueError(...)` directly, or a custom `class ConfigError(ValueError)`
  (7) / `SettingsError` (3). The latter makes the sample invalid under the
  no-classes rule. The settings schema (which keys, typed parsers like
  `_parse_bool`) differs in every sample: median similarity 0.41 (A) and 0.32
  (B), the lowest of all tasks.
- **`token_bucket`** — The most consistent task: all 40 A and B samples use
  `time.monotonic()`, an injectable `now=None`, `min(capacity, …)` refill and
  `elapsed = max(0.0, now - bucket["last"])`; all 20 A samples (12 B) start
  with `bucket = buckets.get(key)`.
  Variants differ in how a missing bucket is initialised and in argument
  checks: 11 shapes but 2 near-shape groups in A.
- **`csv_import`** — Always `csv.DictReader`, a compiled email regex,
  duplicate-email detection (19) and integer age parsing. The email regex itself
  varies (`^[^@\s]+@[^@\s]+\.[^@\s]+$` vs a stricter character-class version),
  but those are literal differences that only affect the exact fingerprint.
  What changes the shape is the set and order of checks and the error format;
  B's paraphrases also change the signature (entry parameters 1–4).
- **`fastapi_create_user`** — Almost always Pydantic models with
  `field_validator`, `Depends`, 409 on conflict and `HTTP_201_CREATED`. Choices
  that vary: `EmailStr` (11 A / 17 B), `@app.post` on a module-level
  `FastAPI()` (16 / 14) vs `APIRouter` (2 / 7), `async def` (17 / 9),
  `Annotated[...]` dependencies (1 / 11).

### Condition C: with a reference

| Task | Effective shapes B → C | Near-shape groups B → C | Reference shape match | Reference exact match |
|---|---|---|---|---|
| `jwt_create` | 20.00 → 3.68 | 11 → 2 | 0.56 (10/18) | 0.56 |
| `password_hash` | 20.00 → 2.67 | 11 → 1 | 0.70 | 0.70 |
| `paginate_query` | 20.00 → 1.65 | 16 → 1 | 0.80 | 0.60 |
| `http_retry` | 20.00 → 1.00 | 18 → 1 | 1.00 | 1.00 |
| `env_config` | 15.00 → 1.48 | 13 → 3 | 0.90 | 0.85 |
| `token_bucket` | 6.79 → 1.00 | 5 → 1 | 1.00 | 1.00 |
| `csv_import` | 20.00 → 3.52 | 18 → 2 | 0.65 | 0.65 |
| `fastapi_create_user` | 2.00 → 1.22 | 2 → 1 | 0.95 | 0.95 |

With a reference, variance collapses: mean effective shapes fall from 17.4
to 2.0, and 6 of 8 tasks reach a single near-shape group.

Samples that differ from the reference are mostly adaptations the paraphrase
asked for, which is what the instruction allowed:
- **`paginate_query`:** all 4 non-matching samples come from paraphrase 5, which asks
  for "items, total, page and page size"; they return `(items, total, page,
  per_page)` instead of `(items, total)`.
- **`jwt_create`:** paraphrase 4 says "expires after some minutes", and all 4 of its
  samples convert minutes to seconds (`int(minutes * 60)`).
- **`csv_import`:** paraphrases 2 and 3 name specific columns and row-keyed errors,
  and 7 of their 8 samples change the checks to match.

The reference also overrides the model's own conventions. In B, 18 of 20 FastAPI
samples defined Pydantic classes. Given a class-free reference, 0 of 20 did, and
19 of 20 matched it.

## Assessment

**What the data shows** (for this model, these 8 tasks, 20 samples per cell):

1. **Asking for the same thing twice almost never gives the same code.** For 6
   of 8 tasks, the identical prompt produced a structurally different
   implementation nearly every time: 17–20 distinct shapes in 20 samples for
   five tasks, and 10 distinct in 10 valid samples for `env_config` (effective
   shapes 10–20). Paraphrasing — the realistic case of different engineers
   asking — pushes every task with enough valid samples except `token_bucket`
   to the ceiling (all valid samples distinct), and lowers median pairwise
   similarity for 5 of those 7 tasks (e.g. `http_retry` 0.76 → 0.50,
   `jwt_create` 0.82 → 0.52; `password_hash` and `token_bucket` rise slightly).
2. **Much of that variance is small, but not all of it.** At the ≥ 90%
   similarity level, `password_hash` and `token_bucket` A collapse to 2 groups,
   but `paginate_query`, `http_retry` and `csv_import` A still have 13–14
   groups, and B has 11–18 for most tasks.
3. **Design choices drift with wording.** Paraphrases change the HTTP library
   (`requests` vs `urllib`), the hashing algorithm (scrypt vs PBKDF2), sync vs
   async endpoints and the dependency style. These are exactly the
   inconsistencies a team would want to settle once.
4. **A reference in the prompt removes most of it.** Effective shapes drop from
   6.8–20 to 1.0–3.7 and 56–100% of samples have the reference's exact shape.
   The rest mostly differ where the paraphrase asked for something different.

**What it suggests, without showing it:**

- The core premise holds for LLM-written code: without guidance, a team
  would accumulate many slightly different versions of the same few functions.
  With a reference available at generation time, output converges on it. This
  is the strongest evidence so far for the catalog-plus-MCP design, much
  stronger than the v2 miner benchmark (which measured existing library code).
- Convergence came from an **arbitrary, unreviewed** reference (B sample 01),
  so the model follows *whatever* it is given. That makes the review
  step essential, not optional: a catalog makes bad patterns just as consistent
  as good ones.

**What would make the case stronger or weaker:**

- *Weaker:* condition C is close to "copy this", and it assumes the right
  reference is always found. If an MCP lookup often returns no reference or the
  wrong one, the real-world effect will be smaller. Other models (or the bare
  API without Claude Code's system prompt) might be either more or less
  consistent. Some of the variance counted here does not matter in practice
  (e.g. `exp + ttl` vs `exp + int(ttl)`).
- *Stronger:* repeat with the API backend and at least one other model; use
  more samples (to get off the 20/20 ceiling); add a retrieval step (the model
  must ask an MCP server and pick a pattern); measure whether condition-C code
  still passes the reference's tests; and test with reviewed catalog patterns
  rather than sampled ones.

## Reproduce

```bash
python scripts/variance.py generate --run-id main --conditions A,B
python scripts/variance.py analyze --run-id main
python scripts/variance.py reference --run-id main
python scripts/variance.py generate --run-id main --conditions C
python scripts/variance.py analyze --run-id main
```

Generation needs `ANTHROPIC_API_KEY` (preferred) or the `claude` CLI. Existing
successful samples are skipped, so use a new `--run-id` for a fresh run.
