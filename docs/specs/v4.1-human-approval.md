1. Goal
In v4, agents wrote every `# pcat-allow` approval themselves, including one that approved retrying a POST request. An approval only means something if a human gave it. v4.1 makes agent-written approvals proposals that keep CI failing until an approver confirms them, closes the marker-deletion loophole, adds the missing 429 guard, and fixes two noisy rules.
Build in this order, committing after each part: A approval binding → B approval states and the CI gate → C marker removal → D guard and rule fixes → E demo pull request → F handoff.
2. Part A — bind approvals to the code they approve
An approval must stop counting if the code it approved changes.

* New approval format: `# pcat-allow: PC100 #<hash> -- <reason>`, where `<hash>` is the first 8 hex characters of the approved function's canonical fingerprint (v1.1 rules).
* If the function's current hash differs, the approval is stale: it no longer approves anything and is reported as a warning.
* The v4 format without a hash is still parsed but treated as stale, with a message showing the hash to add.
* `check_code` (MCP) and `pcat lint` show the current hash next to every deviation, so agents and people can write the line correctly.
* Update the MCP server instructions: agents may propose an approval with the hash and a reason, and must say in their reply that a human needs to confirm it.

3. Part B — approval states and the CI gate
Each approval is one of:

* confirmed: the same approval line (same code, hash and function) exists at the base ref. It already passed review when it merged.
* proposed: new or changed relative to the base ref. It does not approve anything until confirmed in the pull request.
* stale: hash mismatch (Part A).

`pcat lint --changed-since REF` classifies approvals this way. Without a base ref, all approvals are treated as confirmed, and the output says so.
Confirming a proposal in a pull request (GitHub):

* An approver confirms by either submitting an approving PR review or posting a comment containing `/pcat approve`. Either counts only if made after the latest commit of the pull request (compare against the head commit time or review `commit_id`).
* Approvers come from a config file `.pcat/approvers.yaml`: a list of GitHub usernames and/or `codeowners: true` to accept anyone listed in `CODEOWNERS` for the changed file.
* `allow_author: false` by default. When `true` (solo-developer mode), the pull request author may confirm their own proposals. Document that this weakens the guarantee and is meant for development only.
* Add `pcat approvals check --repo OWNER/REPO --pr N` that reads reviews and comments through the GitHub API (`GITHUB_TOKEN`), and exits 1 if any proposed approval is unconfirmed. It must print exactly which proposals are waiting and who may confirm them.
* Ship a workflow example `docs/ci/pcat-approvals.yml` that runs on `pull_request`, `pull_request_review` and `issue_comment` events, so a review or `/pcat approve` comment re-runs the check without a new commit. Install it in this repo's own CI too, with `.pcat/approvers.yaml` set to the repo owner and `allow_author: true`, since there is one developer.

Tests must mock the GitHub API; no live calls in tests.
4. Part C — marker removal
Deleting a marker currently turns a failure into an advisory finding.

* New deviation `PC111` (high): with `--changed-since REF`, a function that had a `# pcat:` marker at the base ref has none now, while it still infers as derived from the same pattern.
* It can be approved like any other deviation, for example when code genuinely stops being based on the pattern.

5. Part D — guards and noisy rules

* New guard kind `must_include`: a constant or default argument that must still contain given values, e.g. `RETRY_STATUSES` must include `429, 500, 502, 503, 504`. Add it to `http.get_with_retry.requests`. It must pass on its own pattern (validation check 11).
* Review guards on the other 6 application patterns for collection constants of the same kind, and add `must_include` where the v2.2 security notes justify it. Record each addition and why.
* PC103 (library swapped): high only when a library in the pattern's `requires` is dropped or replaced. A new third-party import alone is medium. Changes involving only standard-library modules (such as `io`) are low.
* PC110 (other structural change): don't report a line that already carries any other deviation.
* Re-run the v4 replay with these changes and add an addendum to `docs/benchmarks/v4-linter.md`: how the counts changed, in particular how many of the 20 HTTP samples are now flagged for dropping 429. Do not edit the original v4 numbers; the addendum sits below them.

6. Part E — demo pull request
Prove the gate works end to end on GitHub:

* Create a branch with a small example file under `examples/approval-demo/` that uses `http.get_with_retry.requests` with its marker, but narrows retries to timeouts, plus an agent-style proposed approval with the correct hash and a reason.
* Open a pull request to `main`. Confirm CI fails with the proposal listed as unconfirmed.
* Leave the pull request open for the owner. In the final message, explain exactly how to confirm it from a phone (an approving review or a `/pcat approve` comment) and what should happen next.
