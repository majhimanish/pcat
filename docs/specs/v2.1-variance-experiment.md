# v2.1 — LLM output variance experiment

Work unattended. Do not stop to ask questions; when something is ambiguous, pick the simplest reasonable option, record it in `DECISIONS.md`, and continue.

## 0. Before you start

1. Read `CLAUDE.md`, `DECISIONS.md`, `KNOWN_GAPS.md`, every spec in `docs/specs/` and `docs/benchmarks/v2-results.md`.
2. Save this file verbatim as `docs/specs/v2.1-variance-experiment.md`.
3. Run `pytest` and `pcat validate` to confirm a green start.

## 1. Goal

The v2 benchmark measured repetition in existing library code, which is only a proxy. This experiment measures the problem the project actually exists to solve: **when asked for the same thing, how many structurally different versions of the code does an LLM produce?** Then it measures how much giving the model a reference pattern reduces that variance.

Three conditions per task:
- **A, same prompt:** the identical prompt every time (pure sampling variance)
- **B, paraphrased prompts:** different wordings of the same request (like different employees asking)
- **C, with reference:** paraphrased prompts plus a reference implementation (simulates the future MCP lookup)

Build in this order, committing after each part: **A** tooling → **B** generation for conditions A and B → **C** analysis → **D** condition C → **E** write-up and handoff.

Do not change canonicalization, shape fingerprints, the catalog or existing tests. This is an experiment built on top of the existing tools.

## 2. Tasks

Create `experiments/variance/tasks.yaml` with these 8 tasks. Each must ask for **standalone Python functions only (no classes)** so results can be fingerprinted.

1. `jwt_create`: create a signed JWT access token for a user id with an expiry
2. `password_hash`: hash a password and verify a password against a hash
3. `paginate_query`: return one page of results from a SQLAlchemy query, with total count
4. `http_retry`: GET a URL with retries and exponential backoff on failure
5. `env_config`: load and validate settings from environment variables with defaults
6. `token_bucket`: rate limiter check using a token bucket stored in a dict
7. `csv_import`: parse a CSV of users, validate rows, return valid rows and per-row errors
8. `fastapi_create_user`: a FastAPI endpoint function that validates input and creates a user via an injected repository function

For each task, write:
- `prompt`: the condition A prompt, phrased the way an engineer would type it
- `paraphrases`: 5 different wordings of the same request (condition B and C)
- A shared suffix appended to every prompt, defined once in the file: respond with one Python code block only, standalone functions only, no classes, no explanation

Write and commit `tasks.yaml` **before** generating anything, so prompts can't be tuned to the results.

## 3. Part A — tooling

`scripts/variance.py` with subcommands `generate`, `analyze`, `reference`, and `report`. Analysis logic lives in a small importable module (`experiments/variance/analysis.py` or `src/pcat/variance.py`, your choice) so it can be unit-tested.

**Independence matters most.** Every sample must come from a fresh context that has seen only that one prompt. Never generate several samples in one conversation or let one sample see another. Generator backends, tried in this order, first available wins:
1. **Anthropic API** if `ANTHROPIC_API_KEY` is set: model from `--model` (default `claude-sonnet-5-5`), default temperature, one request per sample
2. **Headless Claude CLI** (`claude -p`) if installed: one process per sample
3. **Fresh subagents**: one new subagent per sample, given only the prompt, returning only the code

If none works, stop the generation part, write what's missing into `docs/benchmarks/v2.1-variance.md`, finish the rest of the tooling and tests, and report this in your final message.

Record for every sample: task, condition, prompt text, backend, model (if known), temperature (if known), timestamp, raw response, extracted code.

**Storage:** `experiments/variance/runs/<run-id>/<task>/<condition>/sample_NN.py` plus `sample_NN.json` for metadata. Commit the runs; they're small and make the experiment reproducible.

**Code extraction:** take the first fenced Python code block; if none, the whole response. If it doesn't parse, or contains a class, keep it but mark it invalid with the reason.

## 4. Part B — generate conditions A and B

- 20 samples per task per condition: A uses `prompt` 20 times; B cycles through the 5 paraphrases, 4 samples each
- Total: 8 tasks × 2 conditions × 20 = 320 samples
- Add `--samples N` and `--tasks` flags so a smaller run is possible; run a 2-sample smoke test first
- Retry transient failures up to 3 times; record permanent failures instead of stopping

## 5. Part C — analysis

For each task and condition, using the existing canonicalizer and shape fingerprints on the whole extracted snippet:
- Valid samples, invalid samples (by reason)
- **Distinct exact fingerprints** and **distinct shape fingerprints**
- **Top-shape share**: fraction of valid samples in the most common shape
- **Effective number of shapes**: `exp(entropy)` of the shape distribution (1.0 = perfectly consistent; 20 = every sample different)
- **Distinct import sets** (e.g. `jwt` vs `jose`, `bcrypt` vs `passlib`): library choice is a real source of inconsistency the fingerprints may hide
- **Distinct function counts and entry-point parameter counts**

Also run `pcat mine` over each condition's samples (with `--min-occurrences 1` and trivial-function filtering off) and keep the HTML report for browsing.

## 6. Part D — condition C, with reference

- For each task, pick the reference from condition B: the representative of its most common shape (largest exact sub-group, then lowest sample number). Save it as `experiments/variance/references/<task>.py`. **Do not add references to the catalog**; they are unreviewed.
- Condition C prompt: one of the 5 paraphrases (cycled, as in B) + "Follow this reference implementation; adapt names and details only where the request requires it:" + the reference code + the shared suffix
- 20 samples per task, then the same analysis
- Additional metric: **reference match rate**, the fraction of samples whose shape fingerprint equals the reference's

## 7. Part E — write-up

`docs/benchmarks/v2.1-variance.md`, committed:
- Setup: backend, model, temperature, sample counts, date, and the exact limitations of the setup
- One table: task × condition with distinct shapes, top-shape share, effective shapes, distinct import sets
- Per task, 2–3 sentences on *how* the variants differ (library choice, error handling, structure), with one short example of a difference
- Condition C: reference match rate per task, and how variance changed from B to C
- An honest assessment: does this support the project's idea, and what would make it stronger or weaker? Separate what the data shows from what it suggests.

## 8. Tests

Using small committed fixture samples, not live generation:
- Code extraction: fenced block, no fence, multiple blocks, unparseable code, code with a class
- Metrics on hand-built fingerprint lists: all identical → 1 shape, effective shapes 1.0, top share 1.0; all distinct → N; a known mixed distribution
- Import-set extraction groups `import jwt` and `from jwt import encode` together
- Reference selection is deterministic
- Generator backend selection order (mock the environment; no real API calls in tests)
- Analysis output is byte-identical across two runs on the same samples

## 9. Acceptance criteria

- `pytest` passes on Python 3.11 and 3.13; `pcat validate` passes; CI passes on GitHub
- `tasks.yaml` was committed before the first generated sample (check with git history)
- All three conditions generated with 20 valid-or-recorded samples per task, or the write-up explains exactly why not
- `docs/benchmarks/v2.1-variance.md` exists with real numbers
- No existing fingerprint, catalog entry or test changed
