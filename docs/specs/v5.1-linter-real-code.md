# v5.1 — Linter fixes for real codebases

Work unattended. Do not stop to ask questions; when something is ambiguous, pick the simplest reasonable option, record it in `DECISIONS.md`, and continue.

## 0. Before you start

1. Read `CLAUDE.md`, `DECISIONS.md`, `KNOWN_GAPS.md`, every spec in `docs/specs/`, and everything in `docs/benchmarks/` (especially `v5-open-source.md` and `summary.md`).
2. Save this file verbatim as `docs/specs/v5.1-linter-real-code.md`.
3. Run the full test matrix and `pcat validate` (for `catalog/` and every v5 catalog) to confirm a green start.
4. Leave pull request #1 alone.

**No new agent runs in this phase.** Everything is measured by re-scoring existing data. Do not change canonicalization rules, shape fingerprints, any `impl.py` or fingerprint in `catalog/` or the v5 catalogs, the search threshold, or any earlier experiment data. Re-scored results go to new files.

## 1. Goal

v5 found that the linter misbehaves on real code: 3 of the 5 runs that would fail CI reproduced the original code exactly but tripped a linter bug. Before testing anything new, the linter must be trustworthy on real codebases, because a CI check that fails correct code gets switched off.

Build in this order, committing after each part: **A** name resolution → **B** partial code in `check_code` → **C** `requires` consistency → **D** guard review → **E** false-positive survey on real code → **F** re-score → **G** write-up and handoff.

## 2. Part A — resolve names defined in the same file

Guards and deviation codes currently fail to match names defined in the same module, such as a class `KeyChecker` used by the function under check.

- Build one symbol table per code unit covering: imports and their aliases (`import x as y`, `from a import b as c`), classes, functions and constants defined in the same file, and attribute chains on them.
- Resolve every name a guard or deviation rule refers to through this table, **on both the pattern side and the code side**, so the same thing resolves identically in both.
- A guard target without a module prefix (e.g. `KeyChecker`) matches a same-file definition; a qualified target (e.g. `requests.ConnectionError`) matches an import resolving to it under any alias.
- Reproduce the 3 LNbits false failures from v5 as regression fixtures first, then fix.

## 3. Part B — partial code in `check_code`

Agents often pass a single function without its imports.

- When imports are missing, names that can't be resolved are **unknown**, never treated as a library swap (`PC103`) or a missing call or exception (`PC100`, `PC101`, `PC105`). Rules that depend on unknown names are skipped and the result lists which ones.
- Add an optional `context` argument (the surrounding file's text, or just its import lines) and an optional `file_path` the server may read when it's inside the served repo. With context, resolution works as for a full file.
- The result says whether resolution was full or partial.
- Update the server instructions: pass the file's imports as `context` when checking a snippet.
- Keep v3/v4 behavior for full files; existing tests stay unchanged.

## 4. Part C — `requires` consistency

- Add an optional `import_names` mapping where a distribution's import name differs (e.g. `pyjwt` → `jwt`). Ship a small built-in table for common cases and let `pattern.yaml` override it.
- New validation check 12: every third-party module a pattern imports is covered by `requires`, and every `requires` entry is imported. Standard-library modules are exempt (use `sys.stdlib_module_names`).
- `PC103` uses this mapping, so a library counts as swapped only when the code drops the pattern's required library.
- Fix any pattern in `catalog/` or the v5 catalogs that fails check 12 by correcting **metadata only**; record each fix.

## 5. Part D — guard review

v5 found at least one guard too narrow for a legitimate use (the CTFd reset-token case).

- For every guard that fired in v5, decide: real deviation (keep), or guard wrong for legitimate uses of the pattern (fix the guard). Record each decision with its reason in `DECISIONS.md`.
- A guard may only be loosened when the flagged code is genuinely as safe as the pattern; never loosen a guard to make a number look better.
- Guards are metadata; `impl.py` and fingerprints don't change.

## 6. Part E — false-positive survey on real code

Run `pcat lint --include-inferred` with each app's catalog over the **untouched** app code (the pinned commits in `.bench/apps/`, excluding tests, docs, migrations). No code there carries markers, so every finding is advisory; the question is how noisy the linter is on code humans already wrote.

Report per app: functions checked, functions inferred as derived from a pattern, findings by code and severity, and a manual classification of **every** medium or high finding (or a random sample of 30 per app if there are more) as true deviation, debatable, or false positive, with a one-line reason each. Save under `experiments/v5.1/survey/`.

Fix any false-positive cause found here that is a clear bug, add a regression test, and re-run the survey. Report numbers before and after.

## 7. Part F — re-score existing data

With the fixed linter, re-score without generating anything new:
- v5's 144 end-to-end runs (baseline and pcat)
- the v4.1 feedback rerun (Part A of v5)
- the v4 replay of v3 samples

For each, report what changed versus the original scoring: runs that would fail CI, deviations by code and severity, and every run whose outcome flipped, with the reason. The 3 LNbits runs that reproduced the original exactly must no longer fail. Save under `experiments/v5.1/rescore/`.

## 8. Part G — write-up and handoff

- `docs/benchmarks/v5.1-linter.md`: what was fixed, the false-positive survey (before and after), the re-scoring tables, and an honest assessment of whether the linter is now trustworthy enough to be a required CI check, and what would still make teams switch it off.
- Add a v5.1 section to `docs/benchmarks/summary.md`. Don't rewrite earlier entries; mark any headline that the re-scoring changed and give the new value beside it.
- Update `CLAUDE.md` (at or under 150 lines), `DECISIONS.md`, `KNOWN_GAPS.md` and the README.
- Commit after each part, push to `main`, finish with a clean working tree.

## 9. Tests

- Name resolution: aliases, same-file classes and functions, attribute chains, identical results on pattern and code sides; the 3 LNbits regressions
- Partial code: no `PC103`/`PC100`/`PC101`/`PC105` from missing imports; skipped rules listed; `context` restores full resolution; result reports full vs partial
- Check 12: missing `requires`, unused `requires`, `import_names` mapping, stdlib exemption
- A regression test for every false-positive cause fixed in Part E
