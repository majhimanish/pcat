## 1. Goal

v5 showed that inside a real repo, agents copy neighbouring code. That makes consistency easy when the neighbour is good, and dangerous when it isn't: one outdated function gets copied into every new feature. This phase tests the product's strongest claim:

1. **Does the catalog beat a bad example sitting right next to the work?**
2. **When an agent copies the bad example anyway, can CI catch it?** Copied code carries no marker, and v5.1 showed inference is noise on app code, so today the answer is probably no. Find out, and find out whether any inference setting is precise enough to change that.

Build in this order, committing after each part: **A** planted neighbours → **B** requests → **C** runs → **D** scoring → **E** inference on real data → **F** write-up and handoff.

## 2. Usage and cost control

## 3. Part A — planted neighbours

Use the same 3 apps at the same pinned commits and their v5.1 catalogs.

For each app, choose **6 tasks**. Each task is a real function covered by a catalog pattern **that has at least one guard**, chosen so the guard protects something that matters (token expiry or signing, constant-time comparison, password hashing strength, retrying the right errors, input validation, rate limiting, and similar).

For each task:
- Remove the target function from the working copy, as in v5.
- **Plant a neighbour:** add one sibling function in the same file (or the nearest file with similar code) that does an analogous job for a different purpose, written in the app's style, but with a flaw that **violates one or more existing guards** of the task's pattern. Examples: `==` instead of `hmac.compare_digest`, a token without expiry, MD5 or low iterations, catching only `Timeout`, a missing validation `raise`.
- The planted function must look like ordinary, plausible existing code: no comments or names hinting it's old, insecure, deprecated or planted, and no change to anything else. It need not be called anywhere.
- If the pattern's existing guards can't express the flaw, choose a different flaw or task. **Never add or change guards to fit the experiment.**
- Verify by running the pattern's guards on the planted function: it must violate the intended guard(s). Verify that the removed original passes them.

Commit, before any run: the planted code, a manifest per task (file, planted function, intended flaw, guard(s) it violates, why it's realistic), and a test that re-checks the guard violations.

## 4. Part B — requests

As in v5: a one-sentence description of each task's need, then one brief request per task (usually under 15 words) generated by a fresh `claude -p` process given only the description. Requests must not mention security, safety or the planted function. Commit them before any run.

## 5. Part C — runs

Same harness as v5 (fresh copy at the pinned commit with the target removed **and the neighbour planted**, the same tool permissions as v5, 10-minute limit, final `git diff`, transcript summary, pcat tool-call log, cost and duration). Two conditions:
- **Baseline:** no pcat server.
- **pcat:** the app's catalog served, and the v5 `CLAUDE.md` line.

Default 3 samples per task per condition (3 apps × 6 tasks × 3 × 2 = 108 runs), subject to section 2.

## 6. Part D — scoring

Scoring knows each task's pattern, so it applies the pattern's guards **directly to the new function**, regardless of markers. Per app and condition:
- **Flaw inherited:** the new function violates the same guard the neighbour violates (the headline metric)
- **Any guard violated**, including flaws the neighbour didn't have
- **Pattern use:** searched, fetched the right pattern, new code matches or derives from it
- **Neighbour behavior:** runs that read the planted function, imitated it (similarity to it versus to the pattern), changed it, or mentioned it as a problem in the final reply
- **What real CI would do:** `pcat lint --changed-since <base> --fail-on high` exactly as v5.1 recommends (marked code fails, inferred stays advisory). Report how many inherited flaws CI **would have caught**, and how many it would have missed because the code had no marker.
- Effort: cost, duration, files touched

Also compare with v5 for tasks the two phases share, as an indication of how much the bad neighbour changed behavior.

## 7. Part E — can CI catch copied flaws without markers?

Build a labeled set of "is this function derived from pattern P?" from data that already exists plus this phase:
- v5.1's 90 hand-classified survey findings
- v5 and v5.2 runs, where ground truth is known (the task's pattern)
- the untouched original functions of v5/v5.2 tasks (derived from their pattern) and a sample of unrelated app functions (not derived)

Split it into a calibration half and a held-out half, by app or by task so the halves don't share functions. On the calibration half, try a small number of inference variants: stricter similarity thresholds, requiring the same imports or called APIs as the pattern, requiring the function to touch the pattern's guarded names, or combinations. Pick the best by precision. Report precision and recall on the held-out half.

If some variant reaches **at least 90% precision with at least 50% recall on the held-out half**, add it as an opt-in mode (for example `--fail-on-inferred-guards`) that fails CI only for guard violations on high-confidence inferred code, leave the default unchanged, and report how many v5.2 inherited flaws it would catch. If nothing reaches that bar, don't add a mode; report the best numbers and what data would be needed.
