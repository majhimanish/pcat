# v2.2 — Application pattern catalog

Work unattended. Do not stop to ask questions; when something is ambiguous, pick the simplest reasonable option, record it in `DECISIONS.md`, and continue.

This spec has two parts that run in **separate sessions**:
- **Part 1** (run now): prepare a comparison of the main variants for each of the 8 variance-experiment tasks, with a recommendation, so the human owner can choose.
- **Part 2** (run only when the owner says `choices.yaml` is final): turn the chosen variants into reviewed catalog patterns.

If you are starting this spec and `docs/catalog-review/choices.yaml` has `status: final`, skip to Part 2.

## 0. Before you start

1. Read `CLAUDE.md`, `DECISIONS.md`, `KNOWN_GAPS.md`, every spec in `docs/specs/`, and `docs/benchmarks/v2.1-variance.md`.
2. If not already there, save this file verbatim as `docs/specs/v2.2-app-catalog.md`.
3. Run `pytest` and `pcat validate` to confirm a green start.

Do not change canonicalization rules, existing fingerprints, existing patterns or the experiment data in `experiments/variance/`.

## 1. Goal

The v2.1 experiment showed that the model writes structurally different code for the same request, and follows a reference when given one. It also showed that it follows a **bad** reference just as faithfully. So the catalog's application patterns must be chosen deliberately by a human, not taken from arbitrary samples. This phase builds the first application-level catalog from the 8 experiment tasks, replacing textbook algorithms as the catalog's main content.

## 2. Part 1 — comparison for the owner

For each of the 8 tasks, using the valid samples from conditions A and B:

**Pick 2–4 variants that differ in a design decision that matters**, not in trivia. Group samples by the decisions they make (library, algorithm, sync vs async, error-handling approach, input/return types), not by fingerprint alone. Choose one representative per group, preferring the cleanest sample.

**Clean each variant up.** Fix bugs and security problems, add type hints, and make it fit the catalog rules (standalone functions, literal-only constants, no classes). Keep the design decision intact. Record what you changed. Specific requirements:
- No secrets, keys or URLs as constants; they are parameters
- No network or real clock in tests: inject `sleep`, `now`, HTTP session or similar
- Timezone-aware datetimes; constant-time comparison for secrets; no MD5/SHA-1 for passwords
- Prefer the standard library; when a third-party library is used, name it and its version range

**Security notes**: for each variant, list real risks and what the cleaned version does about them.

**Recommend one variant per task** with 2–3 sentences of reasoning. Mark it in the comparison and pre-fill it in `choices.yaml`.

**`fastapi_create_user`**: catalog patterns can't contain classes, but idiomatic FastAPI uses Pydantic models. Offer these as the options: a class-free variant (validated dict input), and "defer until patterns support classes". Recommend whichever you judge better and explain.

**Output (committed):**
- `docs/catalog-review/v2.2-comparison.md`: Markdown that reads well on GitHub's mobile view. One section per task: a one-line summary of how the samples split (e.g. "11 used PyJWT, 9 used python-jose"), then each variant with label, the decision it represents, how many samples made that decision, the cleaned code, what was changed, security notes, and pros/cons. Recommendation at the end of each section. Keep each code block under ~40 lines.
- `docs/catalog-review/variants/<task>/<variant>.py` with tests in `test_<variant>.py` for each cleaned variant, so every option is proven to work before the owner picks.
- `docs/catalog-review/choices.yaml`:
  ```yaml
  status: draft          # owner changes to: final
  choices:
    jwt_create:
      variant: <recommended label>   # owner may change
      pattern_id: <proposed id, e.g. auth.jwt.create_access_token>
      notes: ""                      # owner's instructions for Part 2
    # … one entry per task
  ```
- Add the variant tests to CI only if their dependencies are installed; otherwise skip them cleanly.

Stop after Part 1. Commit, push to `main`, and in the final message list each task's recommendation in one line, plus anything the owner must decide.

## 3. Part 2 — create the catalog patterns

Run only when `choices.yaml` has `status: final`.

For each task whose choice isn't `defer`:
- Create the pattern from the chosen cleaned variant with the existing tooling (`pcat new`/`pcat add`), using the chosen `pattern_id`. Apply the owner's `notes`.
- Write thorough tests: normal cases, edge cases, failure cases, and the security properties from the comparison (e.g. expired token rejected, wrong password rejected, constant-time compare used).
- **Dependencies:** add an optional `requires` list to `pattern.yaml` (e.g. `["pyjwt>=2.8,<3"]`). It's metadata only and must not affect fingerprints. Extend the schema, include it in `index.json`, and add a `catalog` optional-dependency group in `pyproject.toml` that installs everything the catalog needs. CI installs it.
- Run `pcat fingerprint --write`, `pcat index`, `pcat validate`.

**Seed algorithms:** keep the 6 original seed patterns; they're harmless and well-tested. Note in README that application patterns are now the catalog's focus.

**Coverage check:** re-run the v2.1 analysis comparing condition B samples against the new patterns' shape fingerprints, and add a short section to `docs/catalog-review/v2.2-comparison.md` saying how many of the original samples already matched the chosen pattern. Expect this to be low; it shows the variance the catalog will remove.
